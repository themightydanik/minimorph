# Minimorph technical and game-development audit

Audit date: 8 November 2026. Inspected base: `e7638a2` (`main`, merged PR #16). Scope: repository inspection and official PlayCanvas documentation only. No game/editor changes, dependency changes, asset processing, deployment, tests, builds or benchmarks were performed for this audit. Existing test code and historical evidence were inspected; their presence is not a claim that the current checkout passed them today.

Read alongside [Level Factory architecture](LEVEL_FACTORY_ARCHITECTURE.md), [quality roadmap](GAMEPLAY_QUALITY_ROADMAP.md) and [Cosmic Sprint 2.0 brief](COSMIC_SPRINT_2_DESIGN_BRIEF.md).

## Executive summary

1. **Maturity:** a functional multiplayer vertical slice with substantial reusable foundations, not a release-ready 6–10-level production pipeline. Shared deterministic simulation, three-round tournaments, optimized animated characters, prepared GLB streaming and a useful single-level editor exist. Physical-device performance, release operations and repeatable authoring of independent levels remain unproven or incomplete.
2. **Top ten gaps:** single-level authoring/publication; no versioned gameplay section prefabs; no connection/reachability report; no visual bot route editing; no spawn-anywhere playtest; limited placement/alignment tools; no mechanism scrub timeline; camera/collision constraints for complex geometry; temporary character action presentation; no current real-device performance/release validation. These are ranked in the roadmap rather than treated as ten equal emergencies.
3. **Highest-leverage editor work:** safe playtest start placement, grid/surface snapping and alignment, route overlays/editing, then section instances with connection diagnostics. Collision visualization already exists and should be extended, not reimplemented.
4. **Architecture:** retain `ArenaConfig`, `stepArenaPlayer`, `ArenaRuntime`, GLB instancing and local collider compilation. Add a deterministic, headless section/level compiler and registry in game-content; compile authoring instances into the same runtime arrays consumed by client and server. Separate authoring metadata, gameplay compatibility and presentation identity.
5. **First implementation PR:** a small gameplay/validation contract PR: representative headless movement fixtures, explicit supported-world constraints and a machine-readable validation report for the existing level. No physics retuning. This creates trustworthy gates before generalizing content.
6. **Major risks/decisions:** target phone GPU/texture/skinning budgets; full 3D-looking assets exceeding heightfield-like collision support; global-axis assumptions when rotating sections; bot heuristics on branches/moving supports; content revisions drifting between frontend/backend. Owner decisions include checkpoint/progress policy, player-player collisions, target devices/loading envelope, and final art ambition. None blocks this documentation PR.

## Evidence convention and maturity scale

**V** = verified in source at the base above; **H** = historical repository evidence, not rerun; **R** = recommendation; **U** = unknown until testing or an owner decision. Relative source links resolve from this directory. “Production-ready” below means a narrowly scoped contract is suitably established in source, not that the whole game is certified for release. “Requires refactoring” means a bounded extension seam is needed, not a rewrite.

## 2. Gameplay foundation

| Area | Verified behavior | Player-quality implication and next action |
| --- | --- | --- |
| Acceleration/braking | `SPEED=6`, acceleration 34, deceleration 42; radial input normalized at magnitude 1; air control comes from course. | Rough full-speed ramp 0.176s and stop 0.143s, ignoring boosts/supports. R: measure intent-to-motion and stopping at edges with human input before tuning numbers. |
| Jump/air control | Jump 8.5 m/s, gravity 18 m/s²; 0.10s coyote, 0.12s buffer, edge-triggered jumping. | Foundation is responsive. Ideal equal-height ballistic flight ≈0.944s, apex ≈2.01m and constant-speed 6 m/s travel ≈5.67m. These are analytical bounds, not a validated safe gap or standing-start range. |
| Dive/Slide/Recovery | Capped 8.4 forward speed; downward velocity clamp, limited steering; 0.42s slide, 0.22s recovery, 1.1s cooldown. Start-of-step action guard and held-input latch consume forbidden presses. | No double-jump/additive dive boost. R: preserve the edge/cooldown tests; evaluate perceived lock duration with players rather than undoing consistency fixes. |
| Landing/collisions | Top crossings use old/new Y and support priorities; solid boxes resolve penetration; hazards use sampled primitive contacts. | Good for platformer decks. Limits on thin/high-speed side contacts, slopes, underside collision and decorative walkability must be explicit. R: lint unsupported shapes and add representative swept-contact fixtures before adding complex terrain. |
| Knockback/recovery | Decaying knock X/Z, hit lift, protection and respawn delay; impact strength 2–24 for supported edited hazards; contact latch avoids repeated impulse on continuous configured contact. | Stronger hits can eject players; no ragdoll exists. R: tune telegraph/landing space/strength per section, not a universal camera shake or stronger hits everywhere. |
| Moving supports | Shared `supportDisplacement` handles translations, rotating discs and conveyors; `previousY` supports swept landing. | Existing mechanism vocabulary is useful. R: test phase boundaries, riding/jumping off and multiple players triggering collapse; do not rotate arbitrary mechanisms without compiler support. |
| Bounce/turbo | Jump pads have real surfaces; bounce-platform supports can move; turbo uses bounded multiplier ≤2, max-duration refresh, no multiplicative stack. | Functional. R: reachability profiles must include launch velocity, support velocity and boost expiry; visual pad placement alone is insufficient. |
| Checkpoints/respawn | Grounded enabled-region activation; optional/out-of-order visits; last selected checkpoint used for respawn; finish does not require all checkpoints. | This is intentional current behavior. `courseProgress` still uses checkpoint stage in ordering. R/U: define checkpoint backtracking/branch progress for new levels before relying on ranking as fair route completion. |
| Camera | Damped eye/target, portrait framing, fall-height hold, respawn reframe and partial movement-heading follow; manual yaw drives movement. | No geometry occlusion solver. R: test wide turns, tall scenery and landing readability; add bounded obstruction handling only where observed. Avoid changing movement yaw to match automatic camera follow. |
| Animation | Six approved clips selected from physics; 0.12s transitions. `action-pose.ts` adds temporary Dive/Slide pitch and Recovery blends to Land. | Real integration exists. Dedicated dive/slide/get-up art is still needed; silhouette/contact defects are presentation work and must not rewrite authority. |
| Prediction/authority | Four 120 Hz substeps per 30 Hz command on server and prediction; ack replay; version and round/edition guards. | Strong architecture. R: add per-level digest fixtures and measure correction distance under latency; visual smoothing must never alter simulation state. |
| Remote interpolation | 10 Hz snapshots, 150ms buffer, position/heading interpolation; respawn or >8m teleport snaps. | Functional, with inherent delay. No long extrapolation is promised. R: assess action transitions and packet jitter before reducing the buffer. |
| Bots | Server-only legal input; decisions refreshed every 3 server ticks; authored-route follower quantizes direction, looks ahead and compensates supports. | Same collision/action rules as humans. `navigatePark` returns `dive:false`, normal/hard map to the same route choice; no general route switching/wait annotations. R: author mandatory conservative bot routes and verify completion at multiple start phases. |

Highest-impact low/medium-risk improvements are readable contact/landing metrics, safe restart-at-location, route visualization and validation, followed by camera obstruction tests and dedicated action art. High-risk changes—general physics replacement, player-player collision, universal slope support or rollback networking—are not prerequisites for six good levels using the supported primitives.

## 3. PlayCanvas capability audit

Official documentation was reachable during this audit; engine API pages identified v2.23.3, matching the repository pin. **A** means the integration pattern is present and appropriate, not independently performance-certified. **B** is an available capability to consider after profiling. **C** belongs in our architecture. **D** is unsuitable as a default requirement for this project/target.

| Capability | Category | Current implementation / recommendation |
| --- | --- | --- |
| GLB/glTF containers | A | `ContainerResource.instantiateRenderEntity` for prepared environments and characters; embedded materials/textures and prepared parts retained. No need to import the hosted PlayCanvas Editor or generate a parallel asset system. |
| Instancing/batching | A | `cosmic-scene.ts` hardware instances by asset/part/pulse variant; generic `arena-scene.ts` uses static scenery batches. Skinned avatars share resources but still have separate skin/animation cost; sharing a GLB does not merge eight skin draws. |
| Frustum/distance visibility | A, C | Application bounds and camera culling plus 68/90m gameplay load retention and original 180m depth budget; nearby 28m readiness, Environment distance limits and explicit editor focus. C: content-aware streaming policy belongs here; engine frustum tests are reused. |
| GPU/CPU lifetime | A, B | Explicit buffers/material/container cleanup, reference-counted character asset and late-load guards. B: inspect actual texture/transcoder peaks, driver memory and arena switches; no proof that counters equal resident GPU memory. |
| Anim component/state graphs | A, B | `anim.assignAnimation` and base-layer transitions already used. B: artist-reviewed graph/blend trees for approved clips once dedicated assets exist. A full visual state-graph tool is optional, not a prerequisite. |
| Particles/VFX | A, B | Custom bounded pools (48 sparks, 8 rings, 9 participant slots), soft contact shadows and event suppression exist. B: engine particle systems for selected atmospheric effects after measuring fill rate. Do not replace working pools merely to use an API. |
| Shaders | A | `instanced-normals.ts` corrects nonuniform-scale normals. Keep regression captures on engine upgrades. Custom shader code increases maintenance, so new effects need a measured purpose. |
| Lighting/shadows | A, B | Three fixed artistic directional lights, ambient fill, shadows disabled, faux contact shadows. B: authored atmosphere/lighting presets; selective static/baked lighting or a carefully budgeted shadow experiment. No automatic reduction or blanket dynamic shadow enablement. |
| Post-processing | B, D | No scene-wide postprocessing chain in current engine. B: measure one inexpensive approved effect separately. D: mandatory SSAO, multiple full-screen bloom passes, volumetrics or high-resolution dynamic shadows on low-end Android. |
| Profiling | A, B | `app.stats` draw calls, texture bytes and frame time exported once/second; server timing/backlog counters and profile tools exist. B: engine profiler/MiniStats and GPU timer queries in explicit diagnostics builds, not production telemetry without design. |

## 6. Performance and release feasibility

| Goal | Assessment based on source, not new measurements |
| --- | --- |
| Eight players including bots | Structurally supported: protocol capacity, rooms, shared simulation and remote visuals already implement eight. Eight approved characters alone represent about 1,007,424 triangles before environment (125,928 each, from PR #9 records). Resource sharing does not eliminate skinning/fragment cost. |
| Rich stylized environments | Plausible with current prepared parts/instancing, bounded effects and visibility. Texture residency/transcode peaks, material variants, long sightlines and transparency can dominate. No justification for lowering visual quality automatically. |
| Stable 30 FPS, Redmi Note 8 class | U: not established. Must identify actual device SKU/SoC/RAM, browser and thermal state. Existing software-rendered mobile-emulation captures cannot predict hardware FPS. |
| 60 FPS on faster smartphones | Plausible target, unverified; requires ≤16.7ms end-to-end frame cadence under actual eight-player workload. CPU/skin/GPU/network/frame-pacing contributions must be separated. |
| Three-round tournament | Implemented logically with transition/reconnect/empty-final handling. Long-session memory, live host reconnect and changing arena resources still require device/session verification. |
| 6–10 published levels | Typed runtime supports multiple arenas now; authoring/publication and round selection are the limiting interfaces. Package/delivery size must grow by unique referenced assets rather than per-level copies. |

Historical evidence: [PR #13 evidence](../evidence/cosmic-sprint/README.md) reports SwiftShader samples around 0.8 RAF fps and 240–272 MiB tracked textures. Those are software-browser observations, not physical GPU memory or device estimates. Its 142MB/14-GLB package statement predates editor packaging of the full prepared library; do not quote it as today's bundle size. The prepared asset report lists ~235MB across 23 assets; current transferred/resident totals depend on camera and build and were not remeasured here.

### Lightweight benchmark plan for a later, separate milestone

1. Freeze commit, content digest, device/browser/OS, drawing-buffer/DPR, network/cache state and camera route. Keep approved quality settings; no automatic resolution changes.
2. On the actual Redmi-class phone and one stronger phone, sample 1/2/4/8 approved animated characters in the real level. Include a busy plaza, long vista, particle/transparent decoration scene and an arena switch. Separate render-only diagnostic from a moving authoritative match; both are needed.
3. Use one short warmup and a 60-second normal-clock run per configuration, then one ~10-minute eight-player/tournament thermal session on each device. Record cold-load start once and warm-cache entry separately; no endless benchmark matrix.
4. Record RAF frame-time median/P95/P99, >50ms frames, CPU main-thread time, available GPU timings, draw calls/instances/skinned avatars, texture counters and peak process memory, transfers/time-to-control, server tick P95/backlog and reconciliation distance/RTT. GPU timing may be unavailable/disjoint; label this, do not substitute RAF for GPU time.
5. Proposed gate, subject to owner agreement: Redmi target P95 ≤33.3ms after warmup plus <1% frames >50ms, no sustained thermal collapse or OOM across three rounds. Faster-device target P95 ≤16.7ms. Track cold-load and memory budgets before assigning arbitrary limits. A short passing sample is not a release guarantee.
6. Respond to measured bottlenecks with instancing/material reuse, ownership cleanup, smarter dependency loading or explicitly approved asset work. Do not silently lower resolution, lighting, texture quality or existing scenery.

## 7. Release and economics boundaries

Telegram bridge and browser practice are functional, but physical Telegram WebView, safe areas, audio resume, app suspension and live HTTPS/WSS behavior still require manual release QA. Minima READ-only packaging/adapter exists; live node tests are separate. Android packaging, store policy, signing, lifecycle and network security need their own decisions; a browser game is not yet an Android release artifact.

Authoritative positions/results do not authenticate a human or make a game safe for financial rewards. Keep Minima P2E after stable release/identity/abuse decisions, durable idempotent results and a threat model. Separate game results from signed economic settlement; never put keys, transactions or token decisions in the client or level compiler. No economics implementation is proposed in the first eight PRs.
